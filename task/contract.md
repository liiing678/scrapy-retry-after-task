# Scrapy 爬取任务崩溃恢复

## 起点与目标

仓库是未经功能改动的 Scrapy 2.13.3。已有 JOBDIR 支持正常暂停与续爬，但不能保证进程强杀后的恢复。本题扩展其现有调度与处理链路，不是要求修复一个上游承诺过的能力，也不是另写独立采集器。

新增布尔设置 SCHEDULER_DURABLE，默认 False。True 时使用 JOBDIR 保存崩溃恢复状态；缺少 JOBDIR 须在下载任何请求前清晰报错。功能接入当前 scrapy.core.scheduler.Scheduler 与 ExecutionEngine，现有 Spider 无需显式确认请求。可以新增内部存储组件，不规定存储引擎和文件布局。

## 持久性与故障范围

只要求本机文件系统、单个活动爬虫独占一个 JOBDIR、同一源码版本及配置恢复。故障指父进程对爬虫子进程执行 kill/TerminateProcess，操作系统与磁盘继续正常工作；不要求防断电、磁盘介质损坏、网络文件系统或恶意修改状态。所有已成功返回 True 的 enqueue_request 都在保证范围内，包括尚未开始下载的请求。

成功入队前，完整请求及其去重状态须持久提交。不能出现“已判重，但请求未保存”的窗口。出队不能删除唯一可恢复副本；出队、开始下载、收到响应、开始回调都不是完成确认。重启须自动恢复所有未确认记录，无需重新遍历 start_urls。恢复过程再被强杀，下一次仍能继续。记录损坏或存储写入失败须明确停止本次爬取并保留可恢复信息，不得静默清空作业或退回不可靠模式。

持久完成确认之后，该记录不因后续重启而重放。业务处理已经结束但确认尚未提交时，允许重放。这是至少一次执行保证；不要求任意远端副作用或 item 写入恰好一次，随附样例以主键 upsert 保持落库幂等。

## 何时算处理完成

Response/Failure 进入现有 spider middleware、callback/errback 后，须等输出迭代器完全结束，所有已产出的子 Request 均完成调度决策，并且对应 item 的异步 pipeline 均结束，才能确认原请求。同步生成器、异步生成器、协程 callback/errback 与 Deferred pipeline 都在范围内。不得在 response_received、request_left_downloader 或第一个 item 完成时提前确认。

上游正常处理并记录的下载终止失败、callback/errback 异常、DropItem、item_error 都算该次请求已经处理结束，不因业务异常无限恢复；此时仍须等待已经产出的其他 item 完成。持久存储失败不属于上述正常业务异常，不能沿异常吞掉路径误确认。

下载中间件返回新的 Request（包含 RetryMiddleware 和 RedirectMiddleware）时，先对后继请求完成持久入队或正常拒绝决策，再确认原请求。两步之间崩溃可产生至少一次重放，但不能两边都消失。后继请求、callback 生成的请求、Request.copy/replace 不得继承导致错误确认的内部身份。

重试和重定向上限沿用每条请求保存的 retry_times、redirect_times 计数语义。故障重放可能增加实际 HTTP 次数，不要求跨重启的全局请求次数上限。

## 身份、请求属性与调度

默认 RFPDupeFilter 的请求指纹语义保持不变。已接收的普通请求在排队、在途、已完成和重启后均拒绝普通重复入队；恢复其原记录不再次受自身去重标记拦截。dont_filter=True 的每次成功入队是独立记录，即使 URL、请求体和属性完全相同，也不能合并或相互确认。

恢复保留 Request.to_dict/from_dict 支持的请求字段，包括 method、body、headers、cookies、callback、errback、cb_kwargs、meta、priority、flags、dont_filter 和类信息。内容以入队时的值为准，不由随后下载中间件对同一对象的修改覆盖。内部记录身份不能污染业务 meta，也不能让复制对象与原请求共用身份。

持久模式按 priority 从高到低取出可运行请求，同优先级按成功入队的先后顺序 FIFO；恢复仍按原入队顺序排序，已在途的请求不抢占。此排序是持久模式的明确约定；关闭时保留全部上游队列与起始请求排序行为。这里只比较 scheduler 的 next_request 次序，不要求并发 HTTP 响应按序完成。

不可序列化的请求必须返回 False、产生 request_dropped、记录可识别原因并增加 scheduler/unserializable，不能转入内存队列；失败请求不能留下去重记录，同指纹的后续可序列化请求仍能入队。网络请求开始前即可拒绝不支持的自定义 scheduler、dupefilter、fingerprinter、queue 配置，并列明支持边界；默认配置与本题夹具必须可用。

## 生命周期及兼容性

同一 JOBDIR 的第二个活动爬虫须在下载前报错，且不能改动第一个的状态；原进程被强杀后，新进程可直接取得独占权，不需要人工删除锁文件。可以使用跨平台文件锁库。每个 JOBDIR 独立，不能用全局锁阻塞无关作业。

False 时原有 JOBDIR 文件、内存请求降级、去重器和自定义 Scheduler 行为保持兼容，不强制旧 Scheduler 增加新方法。True 使用专用持久状态；包含旧式非空 requests.queue 或 requests.seen 的 JOBDIR 可以明确拒绝，无须迁移。含持久状态的目录以 False 打开也必须明确拒绝，避免误以为已经继续任务。空目录、正常完成后的再次打开和重复正常关闭应安全。

新增统计至少包括 scheduler/durable/recovered（本次启动恢复的未确认记录数）、scheduler/durable/acked（本次运行成功确认的记录数）、scheduler/durable/pending（当前未确认总数，含排队和在途）。统计不能替代持久记录作为恢复依据；成功跑完时 pending 为 0。

## 可复现检查与交付

task/check_recovery.py 提供本地 HTTP 集成输入；入口、样本规模及初始观测见 README.md。这些脚本是独立于目标实现的合成夹具。保留其输入和断言的含义，不能通过重写夹具、重新灌入所有起始 URL 或在爬虫中实现另一套恢复绕过核心修改。

公开集成检查覆盖正常采集、下载中断、异步 callback 中断、异步 pipeline 中断、同 JOBDIR 空起点恢复和完成后的再次启动。端到端结果需包含全部业务记录；服务端访问日志须证明未确认页被重投递。初始基线在正常采集检查应通过，在恢复检查应暴露能力缺口。

另外补充下列有确定触发点的回归检查，均为完成标准：

| 场景 | 必须观察到的结果 |
| --- | --- |
| 入队返回成功后、出队前强杀；出队后、下载前强杀 | 空起点重启不丢请求，去重不阻碍重放 |
| 正常终止失败、callback 异常、DropItem、异步 item_error | 正常结束，未确认数归零，再次启动不重放 |
| 回调产出多个 item，其中一个完成、另一个仍阻塞 | 此时强杀，原请求仍能恢复 |
| 503 重试与 302 后继入队后、原请求确认前强杀 | 至少有可恢复链路，重试上限和重定向上限语义不变 |
| 相同 URL 两条 dont_filter 请求，其中一条完成 | 另一条仍恢复；copy/replace 的身份独立 |
| 入队时不可序列化、持久写入失败 | 前者不污染去重；后者停止爬取且不误确认 |
| 优先级混排及同优先级重启、POST 与命名回调属性 | 取出次序和完整属性符合上文 |
| 同 JOBDIR 双进程、强杀后重新取得锁 | 并发持有者被拒绝；故障后可恢复 |
| 关闭功能、自定义旧 Scheduler、已有 JOBDIR | 兼容边界符合上文，相关上游测试通过 |

可通过测试夹具或存储边界注入确定的故障；不规定生产代码暴露测试专用 API。验证进程强杀时只终止测试自己创建的子进程。完成实现、针对性测试和用户文档；文档说明设置、恢复边界、至少一次语义、存储格式兼容策略及运行方式。无需实现跨版本迁移、自动清理历史去重记录或性能基准。
